# 验证记录（v0.4.0，以及它之前的 v0.3.0）

日期：v0.4.0 是 2026-11-02（下面第一节）；v0.3.0 的记录（「v0.3.0 的最后一次完整回归」之后各节）是 2026-10-09。环境：一台 Windows 11 x64 电脑（20 核，直连网络），Node 24.18.0，Electron 41.10.7，Playwright 的 Chromium。

这里区分五种不同的验证，它们不能互相代替：

1. **自动化的代码与音频测试**——单元测试和客观音频测量；
2. **真实运行时里的流程**——真实的 Electron、真实的 Chromium、打包后的程序；
3. **用本机模拟的服务跑通的云端 / 大模型流程**——协议和流程是真的，对面的服务是假的；
4. **真实的外部服务**——只有本机 Ollama 做过；
5. **人的判断**——听感、真实账号、安装体验：**都没有做过**。

读结论之前先看最后一节「没有验证的」。

## 简单模式复查（2026-11-02，同日，尚未打包）

仓库主人要求「逻辑、UI 和流程都检查一遍」。复查以三类不懂音乐的用户走完整流程并逐张看截图：① 第一次用的人，1366×768 笔记本上的桌面版（隔离的临时配置，不强制专业模式）：点场景、听、改两次、撤销、下载、在「我的音乐」里找到、播放、删除再撤销、改名；② 手机 390×780，网页版放在子路径的 iframe 里：一句话 → 做一首 → 改 → 下载 → 切到专业模式再切回；另在 321×560、360×640、600×700、806×560、1098×860 的嵌入框里各走一遍；③ 配了云端服务和大模型的桌面版（模拟的服务，同 `cloud-workflow`）：打开 AI 开关 → 付费确认 → 结果 → 修改（再问一次）→ 下载原始音频；大模型失败；有待取回的付费结果时关窗口。然后快速重走专业模式的主要流程（由各套件覆盖）。截图在 `.scratch/review-simple/shots/`（草稿区，不进 Git）。

找到并修复的问题（详细的缺陷表在交付报告里；编号前缀 SR-）：

- **长度说法与播放器不一致**：要 1 分钟、循环按整小节对齐成 62.6 秒时，说明写「1 分 3 秒」而播放器显示 1:02。现在差一小节以内说「约 1 分钟」，其余按播放器时钟的整秒说；改动说明、卡片、底栏都用同一个函数。
- **提示条盖住按钮**：做好之后「做好了，已保存到「我的音乐」」盖住手机上的微调按钮。结果页的消息改在页面里说（那一行、下载按钮自己显示「已保存」），生成成功、失败、本地取消、大模型回退都不再弹提示条；剩下的提示条在简单模式里出现在顶栏下方；模式切换的提示用同一个 key，不再叠加。
- **新作品那一行重复描述**：现在说接下来做什么；保存失败时不说「已经存进」。
- **一键微调交给了大模型**：配了大模型时「快一点」由大模型理解，可能做出别的改动、多等、在付费服务上多花钱。现在按钮只用离线规则；自己写的话才交给大模型（框下注明）。
- **改不了的微调**：「长一点」在 2 分钟、「快一点」在最快时只说「这次没有可以改的地方」，付费作品还会先问一次付费。现在先用离线规则试，改不了就直接说原因，不问不做。
- **新版本被说成「没有改」**：更安静从 0.02 到 0 做出了新版本，说明却是「这次没有可以改的地方」+「撤销」。
- **撤销后「我的音乐」里还是被撤销的那版**：卡片总是最高版本。现在撤销、上一版、下一版会选中那一版（记在作品的修改时间上），卡片、最近做的、播放和下载都用它；载入的那版优先。
- **改名只改一个版本**、**删除 / 恢复说「3 首作品」**：简单模式里整首改名，删除和恢复按首计、用曲名。
- **「我的音乐」里的播放和下载会跳到做音乐页**：现在原地进行。
- **选好的长度做完一首就丢了**：选「30 秒」做一首、「重新挑」回来又是「自动」。现在这次打开期间一直保留。
- 其余：简单模式里能出现的专业措辞（未保存 / 待取回 / 迟到的付费结果横幅、付费服务不支持的时长、大模型没回应的付费问题、损坏记录、保存失败、导出失败、设置里保存大模型、`Ctrl+Enter` 的空发送）都换成了简单模式的说法；失败行按原因说（密钥、余额 / 频率、网络、其他）；帮助在配了大模型时不再说「不联网」；从专业模式切回时下一首新作品回到本地引擎（载入着云端作品时也是）；v0.2 的有结尾作品下载时带专业模式默认的淡入淡出；触屏上的控件都不小于 44 px（顶栏、长度、标题、版本链接、撤销、搜索、卡片标题、底栏播放键）；380 px 以下播放器的时间不再折行。

## 这一轮修了什么（用户看得到的部分）

- **已经付费但没取回的结果不再会被悄悄丢掉**。以前「重新下载」只挂在一条可以点叉关掉的提示上，再点一次生成它也就没了，而关闭窗口时却不再询问。现在它是每个页面顶部一条关不掉的横幅（重新下载 / 放弃这次结果，后者要再确认）；新的付费生成、打开别的作品、新建创作都会先问；主进程自己记着它，持有期间拒绝新的付费请求，关闭时按自己的状态询问；重新加载界面后横幅会恢复。火山引擎的任务在查询连续失败、超时或取消等待之后也不再丢失，「重新下载」会接着查询。
- **制作人的回复说的就是实际发生的改动**。回复由应用比较修改前后的设置写出，两种制作人都一样；大模型自己的话只作为「模型说明」显示，说到了并没有发生的改动就不显示。（验收时真实的本机模型有一次说「降低了鼓的音量」，而那首曲子根本没有鼓。）
- **离线规则读得更准**：「最多 100 bpm」是上限而不是跳到 200；「总长 1 分钟」是总长而不是加一分钟；「鼓别关」「别换乐器」不再照着被禁止的动作去做；「不要 120，要 100」取后者；「快了点」「鼓大了」是抱怨、要反着改；「这次生成得很快」只是一句话。复核语料的通过率按修复者的统计从 446 / 725 升到 716 / 725；这 725 条现在在测试里（其中 9 条的处理见 HANDOFF S07、S11）。
- **循环片段不再偷偷改速度**：速度只在 ±3 % 以内微调，否则保持速度、长度取整小节。说「快 10 bpm」就是快 10。
- **换调不再改写旋律**：同调式的换调是精确移调；旋律是否保留由作曲器实际比较两版之后说出（四种说法）。
- **服务不接受的时长先问**：选了火山引擎时 15 秒不可选；别处来的 15 秒在付费确认之前就会问。
- **付费确认不会被连点或按住的回车误触**：出现后的半秒内不接受点击和回车。
- **凭据文件损坏不再把设置锁死**：坏文件另存为副本，凭据从空白重新开始，并提示一次。
- 其他：没应用的「声音微调」修改重启后还在；窄窗口里卡片滚出屏幕时有「N 项未应用」的小条；和弦条上不再漏印放得下的和弦名；撤销删除正开着的作品会把它重新打开；「换一版旋律」如实说和弦走向也重写了；等待托管大模型时不再说「本机模型」；风格按钮只占一个 Tab 位。

| 软削波前的采样峰值 | 不超过限制器上限（约 −1.9 dBFS） | −5.9 到 −2.0 dBFS |

**混音平衡**（三个 `tests/style-mix-*.test.ts`，46 项）：按流行 / 原声、律动 / 电子、电影 / 氛围三组，把混音评审定下的每个风格的平衡（旋律在和声之上多少、贝斯和鼓相对混音的位置、明暗、宽度、段落对比、循环首尾是否均匀）钉成约 ±1.5 LU 的窗口。全部通过。

**摇滚能量的平衡在这一轮移动了**：作曲器的修复改了它的旋律。集成时用 `npm run audit:audio -- --style rock --both --seed 1234 --duration 30` 测得四条分轨（旋律 / 和声 / 贝斯 / 鼓组）循环是 −20.2 / −24.1 / −24.0 / −21.0 LUFS、完整结尾是 −20.4 / −24.2 / −23.8 / −20.7 LUFS，混音 −16.00 LUFS、0 个越界项；第二轮评审时定下的循环是 −21.0 / −23.5 / −23.3 / −20.6。也就是主奏靠前约 0.8 LU，其余三条低 0.4–0.7 LU。它仍在门槛和混音测试的窗口之内，但已经不是评审过的那个平衡，需要用耳朵判断。

**音色和鼓**（`voices-*`、`drums`、`fx`、`render` 等）：每个音色在参考力度下最响的 400 ms 约 −18 dBFS、音高误差在 10 音分内、起音和尾音没有台阶；鼓的电平、力度律和频谱特征；混响的衰减时间；母带的增益曲线让分轨之和等于母带后的混音。全部通过。

**示例**（`demos/`）：集成时用 `npm run demos` 重新渲染了全部 22 段（25.3 秒）。22 个 WAV 与作曲器修复后生成的那一批逐字节相同；`index.md` 只有可爱俏皮的那句编曲说明变了（引号改成「」）。响度 −16.01 到 −15.99 LUFS，峰值 −5.9 到 −2.5 dBFS。`examples/` 里的示例没有变（`tests/examples.test.ts` 通过）。

**循环对齐后的实际长度**（集成时用 `planTiming` 对 22 个默认预设逐个算出）：所选 15 秒的循环实际 12–17.1 秒，30 秒的 28.2–32.7 秒，60 秒的 56.5–64 秒，120 秒的全部正好 120 秒；速度被微调的只有落在 ±3 % 以内的那些（例如动感电音 126 → 128 BPM）。

**内存**（集成时在最终代码上重测，Node 24.18，120 秒的渲染，不强制回收，MB 按 2^20 字节计）：默认的氛围冥想预设做成循环时，工作内存的峰值是 **399 MB**（引擎报告的 `bufferBytes` 是 397 MB，进程常驻内存峰值约 450 MB）；史诗燃向的完整结尾 308 MB，青春欢快的循环 305 MB；30 秒的青春欢快循环 88 MB。四条 120 秒的分轨本身是 176 MB，交出之后工作内存全部释放。早先文档里的「约 310 MB」低估了长音很多的曲子。网页版在手机上渲染 120 秒时，这个量级加上页面里的两份分轨很可能超出移动浏览器肯给一个标签页的内存——没有在真实手机上测过，手机上建议用 15–60 秒。

**更早的大范围测量**（第二轮引擎收尾时做的，之后引擎和作曲器都有修改，没有重做）：396 次极端设置的渲染（情绪能量、旋律丰富度、空间混响各取 0 和 1，50 和 200 BPM，15 秒）响度在 −16.25 到 −16.00 LUFS，没有爆音；唯一的欠量是可爱俏皮 50 BPM 循环（0.25 LU）。44 次 120 秒的渲染 −16.01 到 −16.00 LUFS。

**没有达到评审目标的**：评审希望舞曲和摇滚的峰值因数压到 8–11 dB，实际是 11.7–14 dB 左右；流行和原声风格在 14–17 dB。再压就要让限制器明显工作，所以停在这里。这些值都在质量门槛之内，听起来是否「不够紧」只能靠耳朵判断。

**性能**（第二轮的测量）：120 秒的渲染在 Node 里 0.65–5.6 秒；在 Electron 的 Worker 里常见风格 2.7–5.8 秒，最重的史诗燃向单次测得 8.46 秒；Worker 路径下 120 秒渲染期间主线程最长间隔约 40 ms，没有长任务。跟进阶段在 Chromium 里测得 120 秒的 WAV 导出没有 50 ms 以上的主线程任务。

## 换行符（全新 Windows 克隆）

`.gitattributes` 把文本固定为 LF（`*.cmd` 为 CRLF）。验证方式（第一次整理时做的，这一轮没有重做）：把当时的工作区做成一个临时仓库，再用 `git clone -c core.autocrlf=true` 克隆——306 个文本文件检出为 LF，`启动音序.cmd` 为 CRLF，6 个二进制文件不变；在克隆里 `npm test` 为 748 + 219 全部通过。去掉 `.gitattributes` 的对照克隆里，全部文本检出为 CRLF，`tests/examples.test.ts`（逐字节比较示例工程）失败。

## 没有验证的

- **真人用户用简单模式**：简单模式按「完全不懂音乐的人」设计，复查时按三类这样的用户走过完整流程并逐张看了截图，但没有任何真正的用户用过。
- **真实付费的云端音乐服务**：腾讯云、火山引擎、阿里云、ElevenLabs 的账号权限、配额、实际音质、实际时长和账单。模拟服务只保证协议和流程；服务商错误响应的形状来自文档。**这一轮新增的保护同样只对着模拟服务跑过**：火山引擎的续查从没遇到过真实的查询接口；「请求没有发出」是在真实的计费连接上人为造出来的，网络服务自己丢掉回答的情形没有复现。
- **ElevenLabs 没有界面层的端到端自动化**：四家服务里，腾讯、火山、阿里各有一次经界面的完整生成；ElevenLabs 只有单元测试和计费请求实验。
- **真实的托管大模型**：没有用过真实的 Anthropic 密钥，也没有用过任何真实的 OpenAI 兼容服务。各预设的接口地址和密钥页链接没有逐个验证。
- **安装包本身**：`Muse-BGM-Setup-0.4.0-x64.exe`（和之前的 0.3.0）没有运行过（安装、快捷方式、卸载、安装路径都没有测）。被测试的是和它同一次打包生成的 `release/win-unpacked` 以及便携版 EXE。两个 EXE 都没有代码签名。
- **原生对话框**：关闭确认和凭据文件被另存的提示在套件里被换成了记录器，只确认了它们会在什么时候、以什么内容弹出。

- **听感**：没有任何人听过生成的音频。上面的音频结论全部是测量值；这一轮改过的旋律（删稀后的声部进行、换调时折回八度的音）和摇滚能量移动了的平衡同样没有人听过。
- **真实的系统代理、Windows 10、macOS / Linux**：只在一台直连网络的 Windows 11 电脑上构建和测试过。
