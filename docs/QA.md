# v0.3.0 验证记录

日期：2026-10-09。环境：一台 Windows 11 x64 电脑（20 核，直连网络），Node 24.18.0，Electron 41.10.7，Playwright 的 Chromium。

这里区分五种不同的验证，它们不能互相代替：

1. **自动化的代码与音频测试**——单元测试和客观音频测量；
2. **真实运行时里的流程**——真实的 Electron、真实的 Chromium、打包后的程序；
3. **用本机模拟的服务跑通的云端 / 大模型流程**——协议和流程是真的，对面的服务是假的；
4. **真实的外部服务**——只有本机 Ollama 做过；
5. **人的判断**——听感、真实账号、安装体验：**都没有做过**。

读结论之前先看最后一节「没有验证的」。

- 合成与母带：每个音色的契约（电平、音高、起音、尾音、无爆音）、鼓、效果、渲染、内存占用、WAV 编码；22 种风格的质量门槛和三组混音平衡；旧引擎输出与 0.2 逐位一致；Worker 协议与导出。
- 应用内核：任务锁、取消、草稿与已生成作品的分离、付费确认、大模型失败后的询问、保存失败后的保留与重试、「重新下载」、多标签页、撤销删除、导入导出、损坏记录、会话恢复。
- 存储：真实的 IndexedDB 语义（fake-indexeddb）、按字段更新、各种失败的中文说明。
- 界面逻辑：文案统一、时间轴与和弦标注、焦点、提示框、建议按钮只在听得出区别时出现。
- 主进程：四家服务的请求契约、火山签名与轮询、下载重试与域名限制、计费通道、凭据加密与迁移、IPC 来源校验、CSP、网络封装、关闭确认、右键菜单、接口地址与受限端口、大模型两个适配器、桥与契约一致。

**云端与大模型流程**（`scripts/cloud-workflow.cjs`）：真实的界面、preload、IPC、适配器、解码、存储和导出，只把主进程的网络换成本机模拟。没有凭据时拒绝；腾讯 / 火山 / 阿里三家的凭据经界面加密保存；**付费确认**（取消和 Esc 都不发请求）；HTTP 401 的中文说明且不重试；等待中取消；三家各一次完整生成（先保存再解码、显示真实时长、原始文件逐字节不变）；发出的请求符合纯音乐契约、下载不带凭据；**阿里云「音乐已生成但下载一直失败 → 重新下载」，全程只有一次计费请求**；服务不支持的时长在发送前拒绝；无法解码的音频仍保存并可导出；云端作品的修改是同一服务上的新付费版本；删除一家凭据不影响其他；Claude（模拟）规划新作品与修改；模型失败（HTTP 500）回退到规则；等待模型时取消；OpenAI 兼容接口（模拟 DeepSeek，含 401 回退）；模型 + 云端引擎。结束时核对：未知请求 0、Chromium 外发请求 0。ElevenLabs 不在这个套件里，它的覆盖来自单元测试和桌面冒烟里的计费请求实验。

**发行程序冒烟**（`scripts/packaged-smoke.cjs`）：见「发行程序」。

## 音频：测了什么，目标和结果

开发过程中没有人听过引擎的输出。下面的每一条都是对渲染结果的测量，说明的是「数字在范围内」，不是「好听」。

**质量门槛**（`tests/audio-quality.test.ts`，最后一轮 `npm test` 的输出）：22 种风格，每种渲染一个循环片段和一个完整结尾，各 20 秒，种子 20261，默认推子，共 44 次渲染。

| 项目 | 目标 | 测得（44 次渲染的范围） |
| --- | --- | --- |
| 积分响度（BS.1770） | −16 LUFS ±0.3，母带没有欠量 | −16.02 到 −16.00 LUFS |
| 软削波前的采样峰值 | 不超过限制器上限（约 −1.9 dBFS） | −5.9 到 −2.0 dBFS |
| 真峰值（4 倍过采样） | ≤ −1 dBFS | 全部通过 |
| 峰值因数 | 9.5–18.5 dB | 11.7–17.1 dB |
| 频谱斜率（倍频程带，粉噪 = 0） | −5 到 +0.3 dB/倍频程 | −3.92 到 −0.73 |
| 左右声道相关性（混音） | ≥ 0.35 | 0.585–0.983 |
| 循环接缝处的样本台阶 | ≤ 平常的 1.5 倍 | 0.01–0.39 倍 |
| 完整结尾的最后 50 ms | ≤ −90 dBFS | ≤ −117.8 dBFS |
| 爆音、直流、每条分轨可闻、旋律不被和声盖住、80 Hz 以下居中、限制器动作、同一设置两次渲染逐位相同 | 见 HANDOFF S06 的门槛表 | 全部通过 |

**混音平衡**（三个 `tests/style-mix-*.test.ts`，46 项）：按流行 / 原声、律动 / 电子、电影 / 氛围三组，把混音评审定下的每个风格的平衡（旋律在和声之上多少、贝斯和鼓相对混音的位置、明暗、宽度、段落对比、循环首尾是否均匀）钉成约 ±1.5 LU 的窗口。全部通过。

**音色和鼓**（`voices-*`、`drums`、`fx`、`render` 等）：每个音色在参考力度下最响的 400 ms 约 −18 dBFS、音高误差在 10 音分内、起音和尾音没有台阶；鼓的电平、力度律和频谱特征；混响的衰减时间；母带的增益曲线让分轨之和等于母带后的混音。全部通过。

**示例**（`demos/`）：写这份文档时用 `npm run demos` 重新渲染了全部 22 段（26.7 秒），与 `demos/` 里的文件逐字节相同；响度 −16.01 到 −15.99 LUFS，峰值 −5.9 到 −2.5 dBFS。

**更早的大范围测量**（第二轮引擎收尾时做的，之后引擎还有修改，没有重做）：396 次极端设置的渲染（情绪能量、旋律丰富度、空间混响各取 0 和 1，50 和 200 BPM，15 秒）响度在 −16.25 到 −16.00 LUFS，没有爆音；唯一的欠量是可爱俏皮 50 BPM 循环（0.25 LU）。44 次 120 秒的渲染 −16.01 到 −16.00 LUFS。

**没有达到评审目标的**：评审希望舞曲和摇滚的峰值因数压到 8–11 dB，实际是 11.7–14 dB 左右；流行和原声风格在 14–17 dB。再压就要让限制器明显工作，所以停在这里。这些值都在质量门槛之内，听起来是否「不够紧」只能靠耳朵判断。

**性能**（第二轮的测量）：120 秒的渲染在 Node 里 0.65–5.6 秒；在 Electron 的 Worker 里常见风格 2.7–5.8 秒，最重的史诗燃向单次测得 8.46 秒；Worker 路径下 120 秒渲染期间主线程最长间隔约 40 ms，没有长任务。跟进阶段在 Chromium 里测得 120 秒的 WAV 导出没有 50 ms 以上的主线程任务。

**包的内容**：`app.asar` 4,722,660 字节、1156 个条目（1051 个文件）。没有文件过滤规则时，同一份代码打出来是 13,320,817 字节、3005 个条目（2851 个文件）；去掉的 1800 个文件全部是依赖里的源码映射、TypeScript 源码与声明、README 和 SDK `src/` 下的 `tsconfig.json` / `.keep`，留下的 1051 个文件与未过滤的包逐字节一致。Claude SDK 留下 573 个文件：284 个 `.js`、284 个 `.mjs`、`package.json`、`LICENSE`、`bin/` 下两个文件，以及有意保留的 `src/internal/qs/LICENSE.md`。把过滤前后的包分别解到项目之外再逐个加载：SDK 的 281 个 CommonJS 模块和 281 个 ES 模块都能加载，各有 3 个加载不了的是需要 `zod` 的辅助模块（应用不用，也没有安装 `zod`），过滤前后完全相同；用假的 `fetch` 经客户端发出稳定接口和 beta 接口各一次请求，并得到了正确的错误类型。两个 EXE 只小了约 0.58 MB（去掉的文本压缩率本来就高）。

**发行程序冒烟**（`scripts/packaged-smoke.cjs`，23 步，26.3 秒）：先核对包——`dist/`、`electron/`、`package.json` 与工作区一致，依赖里没有多余文件，SDK 的脚本一个不少，`SHA256SUMS.txt` 和发布说明里的校验值就是这两个 EXE 的（改错一位的对照会失败）；再对 `release/win-unpacked/Muse BGM.exe` 和便携版 EXE 各跑 11 步：已打包、版本 0.3.0、隔离的数据目录；13 个桥方法、渲染层没有 Node；CSP 在页面里并且生效；在渲染 Worker 里作一段曲子并播放；对话修改出第 2 版（同一旋律种子）；经保存路径导出 48 kHz / 16 位 / 立体声 WAV；用真实的 Windows safeStorage 保存、再删除腾讯和 Claude 的凭据；包内的 Claude SDK 从 `app.asar` 加载并完成一次模拟的规划；整个进程重启后三件作品还在、可以打开播放；没有渲染层错误，没有任何请求离开本机。便携版是从它自解压出的临时目录运行的。

**这一轮修掉的一个测试竞态**：便携版要靠手工打开的调试端口来驱动。调试端口在 Node 还没有主模块时就能连上，这时注入测试钩子会失败（`Cannot read properties of undefined (reading 'require')`）。`tests/helpers/electron-harness.cjs` 现在先等主模块就绪。对照：去掉这个等待，便携版的 6 次运行里 4 次失败；加上之后 9 次运行全部通过。这是测试工具的问题，不是程序的问题。

**启动脚本**：`启动音序.cmd` 只用 `MUSE_LAUNCHER_DRY_RUN=1` 检查过会选哪个文件（打印 `release\Muse-BGM-Portable-0.3.0-x64.exe`），没有用它真正启动过程序。

## 换行符（全新 Windows 克隆）

`.gitattributes` 把文本固定为 LF（`*.cmd` 为 CRLF）。验证方式（整理阶段做的）：把当时的工作区做成一个临时仓库，再用 `git clone -c core.autocrlf=true` 克隆——306 个文本文件检出为 LF，`启动音序.cmd` 为 CRLF，6 个二进制文件不变；在克隆里 `npm test` 为 748 + 219 全部通过。去掉 `.gitattributes` 的对照克隆里，全部文本检出为 CRLF，`tests/examples.test.ts`（逐字节比较示例工程）失败。这项检查在打包阶段之后没有重做。
